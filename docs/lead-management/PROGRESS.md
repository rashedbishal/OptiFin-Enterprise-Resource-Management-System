# Lead Management Development Progress

This document is the authoritative handoff state for ongoing Lead Management enhancement work in this repository. It exists so a new Claude CLI session (or a new engineer) can pick up the work tomorrow without needing this conversation's history.

## 1. Development Workflow / Rules

Every Lead Management enhancement — no exceptions — follows this process:

1. **Inspect** — read the actually-relevant models, migrations, controllers, services, routes, policies/permissions, jobs/events/listeners, notifications, frontend components, existing tests, and DB relationships for the feature at hand.
2. **Impact Analysis** — explicitly reason about what existing behavior the change could touch.
3. **Architecture Proposal** — explain the planned approach (data model, triggers, UI, permissions, risks) before writing any code.
4. **Wait for User Approval** — do not proceed past the proposal until the user explicitly approves it. Open decision points get asked as explicit questions, not silently assumed.
5. **Implementation**
6. **Testing** — comprehensive tests for the new feature, covering success paths, edge cases, permission boundaries, and tenant isolation.
7. **Regression Verification** — Pint, PHPStan, the new feature's own tests, the full `tests/Feature/Leads/` suite, and the full application suite. Confirm no pre-existing behavior changed.

**Never skip directly to implementation for a new feature.**

Core principles:

- Preserve all existing functionality. Additive-only wherever possible.
- Implement one feature at a time — do not bundle multiple roadmap items into one change.
- Avoid scope creep. Build exactly what was approved, nothing more.
- Do not modify unrelated code, routes, permissions, or UI.
- Proactively identify risks and architectural conflicts before they become bugs — surface them in the proposal, not after implementation.
- Do not reopen a completed/approved feature unless a real blocker or regression is discovered by a later feature. A completed feature's own backlog items (see §7) are deferred, not reopened, until the user asks for them.

## 2. Current Lead Management Baseline

The Lead Management module (pre-existing, before Features #1/#2 in this document) is a **Blade/Livewire** module — no React, no separate frontend framework — built on this app's Tenant/TenantUser/Role/Module/Permission stack, ported from a sibling project (`OpticoreLeadManagementHub`).

Implemented baseline capabilities:

- **Multi-channel lead capture**: Facebook Messenger, Instagram, WhatsApp, Facebook Lead Ads, Website Form, Email (IMAP polling via `leads:fetch-emails`), LinkedIn Lead Gen (Phase 1, manual token entry). All via `App\Http\Controllers\Api\LeadWebhookController::createLead()` (5 call sites) or `App\Jobs\ProcessEmailLeadSource`. Each fires `App\Events\LeadReceived` exactly once, on creation.
- **Manual lead creation**: `App\Actions\Tenant\CreateManualLead` — lazily provisions a per-tenant "Custom" `LeadSource`. Does **not** fire `LeadReceived` (a pre-existing, known gap — see §5's manual-lead scoring workaround for how Feature #2 handled this without fixing it).
- **Status pipeline**: `App\Models\LeadStatus` — Platform-Admin-managed shared catalog, attached per-tenant via a pivot with per-tenant `position` ordering; has an `is_closed` flag. Full history in `LeadStatusLog`.
- **Kanban**: `App\Livewire\Tenant\Leads\Index` renders either the table (Client Admin) or the Kanban board (Client User) from the same `filteredQuery()`/`FiltersLeadsQuery` concern.
- **Lead assignment/distribution**: `App\Services\LeadAssignmentService` — manual assign/unassign, plus automatic round-robin / least-loaded / random distribution, driven by `Tenant::lead_distribution_mode`/`auto_distribution_method` (configured Platform-Admin-side). Full history in `LeadAssignment`.
- **Notes**: `App\Models\LeadNote`, freeform, tied to a `TenantUser`.
- **Attachments**: `App\Models\LeadAttachment`, downloaded async via `App\Jobs\DownloadLeadAttachment`, stored on the private `local` disk.
- **Activity timeline**: `App\Livewire\Tenant\Leads\Show::activity()` aggregates `LeadStatusLog`, `LeadAssignment`, `LeadNote`, `LeadDetailUpdateLog` (+ now `LeadDuplicateLink` merge events, +Feature #1) into one chronological feed.
- **Meetings/follow-ups**: `meeting_date`/`meeting_time` (time is record-only, never drives the alert), `next_follow_up_at`, live non-persisted Kanban-card shimmer alerts (`meetingAlertActive()`/`followUpAlertActive()`), tenant-configurable enable + days-before threshold, daily `leads:send-alert-notifications` sweep persists bell notifications.
- **Notifications**: `NewLeadNotification`, `LeadAssignedNotification`, `MeetingUpdatedNotification`, `MeetingCancelledNotification`, `MeetingAlertNotification`, `FollowUpUpdatedNotification`, `FollowUpCancelledNotification`, `FollowUpAlertNotification` — all real-time via Reverb through `App\Listeners\BroadcastUserNotification` on Laravel's internal `NotificationSent` event.
- **Multi-currency budget/deal fields**: `estimated_budget`/`estimated_budget_currency_id`, `deal_value`/`deal_value_currency_id`, `win_probability` — `App\Models\Currency` is a Platform-Admin-managed shared catalog, tenants opt in via `tenant_currencies`.
- **Excel export**: `App\Exports\FacebookLeadAdsExport` (`maatwebsite/excel`) — currently the only export, mirrors the Facebook Lead Ads spreadsheet view's dynamic per-form-field columns.
- **Permissions**: `App\Policies\LeadPolicy` (`viewAny`/`create`/`view`/`update`/`delete`/`assign`, +`merge` from Feature #1). `PermissionSlug` is a **fixed, global 4-value enum** (`View`/`Create`/`Update`/`Delete`) — not extensible per module without a much larger cross-cutting change. Every new capability added by Features #1/#2 reuses the existing `lead-management` module's `update` permission + `isClientAdmin()`, never a new slug.
- **Tenant isolation**: `App\Concerns\BelongsToTenant` adds a global scope, but it **only activates when `app()->bound('currentTenant')`** — which is **not** the case in public webhook/job/command contexts. Every new query in Features #1/#2 filters `tenant_id` explicitly rather than relying on the trait alone. This is the single most important correctness rule for any future Lead Management feature touching cross-lead queries.
- **Architecture discovered during inspection** (load-bearing, apply to any future feature):
  - `Lead::identifier` is monotonic and never reclaimed (`{tenant.lead_id_prefix}-LEAD-{n}`, generated in `Lead::booted()`'s `creating` hook) — never mass-assignable, never reused even after deletion/merge.
  - A background/event-driven write to a `Lead` column must use a **raw query builder update** (`DB::table('leads')->where(...)->update(...)`), not `$lead->save()`, when it must not touch `updated_at` — otherwise it spuriously trips `Lead::hasUnseenUpdate()`'s "recently updated" highlight for every viewer. Established by `Lead::markUpdateSeen()`, reused by Feature #1's merge (loser update) and Feature #2's score writes.
  - `App\Livewire\Tenant\Leads\Index` excludes Facebook Lead Ads leads from the Client Admin's table (aggregated into `SourceLeads` instead) but shows them as normal Kanban cards for Client Users.
  - No reporting/dashboard exists anywhere for leads — `App\Livewire\Tenant\Dashboard` shows only tenant/module/user/role counts, zero lead data. The only existing aggregation is `Lead::countsByStatus()` for Kanban column headers.
  - No `EventServiceProvider` exists — Laravel 11+ auto-discovers listeners from their `handle()` method's type-hinted event parameter.
  - `Auth::user()` is typed `PlatformUser|TenantUser|null` by Larastan throughout the whole app (a pre-existing, accepted, unfixed limitation — confirmed identical in pre-existing files like `Roles/Index.php`) — don't try to "fix" this pattern in new code; it's baseline noise, not a real bug.

## 4. Feature #1 — Duplicate Detection & Merge

Final approved architecture and decisions (do not re-litigate without a real blocker):

- Cross-channel duplicate detection by normalized email/phone match, same-tenant only — `App\Services\LeadDuplicateDetectionService`. Writes/reuses `App\Models\LeadDuplicateLink` rows (`pending`/`dismissed`/`merged`), canonically ordered by ULID pair (`LeadDuplicateLink::pairKeys()`) so a pair is never re-flagged after a dismissal.
- **Merge behavior**: `App\Services\LeadMergeService::merge()` reparents the loser's child records (notes, attachments, status logs, assignments, relevant `LeadDetailUpdateLog` entries) onto the survivor, then marks the loser `merged_into_lead_id` — **no hard delete, no identifier reuse**. The loser stays fully queryable but is excluded from normal list views (`Index::filteredQuery()`, `SourceLeads::baseQuery()`); opening the loser's own detail page redirects to the survivor.
- The whole merge runs inside **one `DB::transaction()`** — verified with a real mid-transaction FK-failure test proving full rollback (no partial state).
- **Conflict values require explicit selection** — `LeadMergeService::conflictingFields()` only flags fields where the loser has a real, differing, non-empty value; the default resolution is always "keep survivor" unless the admin explicitly picks "use loser's value." Fields not in the mergeable allow-list (pipeline/relationship columns: `status_id`, `assigned_to`, `source_id`, `priority`, dates, etc.) are **never** touched by a merge.
- Audit trail: `LeadDuplicateLink` stores `resolved_by`, `resolved_at`, `status = merged`, and `field_resolutions` (a snapshot of every conflicting field's chosen side plus both leads' values at merge time).
- **Duplicate badge is detail-page only** — never on the leads table or Kanban card (a deliberate scope decision, not a limitation to "fix").
- Permissions: `LeadPolicy::merge()` reuses `update` + `isClientAdmin()` — no new permission slug. This became the template every later capability (including Feature #2) copies.

**Explicit backlog, not a current blocker** (see also `.claude`/memory: `project_lead_merge_backlog.md`):
- Duplicate-detection query performance — `LeadDuplicateDetectionService::detectFor()` scans all of a tenant's contactable leads in PHP; confirmed via `EXPLAIN` against real Postgres that the `(tenant_id, email)`/`(tenant_id, phone)` indexes aren't effectively used for this. Future fix: Postgres functional/expression indexes + SQL-level normalized matching.
- Merge budget/currency pairing — `estimated_budget`/`estimated_budget_currency_id` (and the `deal_value` pair) are resolved as fully independent choices in the merge UI, allowing a mismatched amount+currency. Future fix: pair them into one selection.
- **Intentional, documented UX trade-off (not a bug)**: when the survivor's field is empty and the loser has a value, the conflict still defaults to "keep survivor" (stays empty) rather than auto-filling — uniform, non-destructive-by-default behavior, at the cost of requiring the admin to notice and act.

**Do not modify Feature #1 unless a future feature causes a real regression.**

## 5. Feature #2 — Lead Scoring Phase 2a

Final approved implementation:

- Score is a **nullable integer, 0–100**. No active rules for the tenant → `lead_score = NULL` ("Not scored"). At least one active rule → always a real, deterministic 0–100 integer (including a legitimate computed 0).
- Rules carry **signed integer points** (no per-rule min/max) — the final total is hard-clamped to [0, 100], not scaled/normalized (scaling would make unrelated leads' scores drift whenever a rule is added elsewhere, which breaks explainability).
- **Raw total (pre-clamp) is preserved** in `LeadScoreLog.raw_total`, alongside the clamped `score`.
- **Every recomputation is from scratch**: current Lead state + current tenant's active rules + current time — `LeadScoringService::computeFor()` never increments/decrements the previously stored score. Verified deterministic (same inputs → same output across repeated calls) and non-accumulating.
- A `LeadScoreLog` row is written **only when `(score, breakdown)` actually differs** from the lead's last log — trigger reason is metadata, not part of that comparison. This keeps the log table's growth proportional to real change, not event volume.
- `breakdown` is a **point-in-time snapshot** (rule name/field/operator/value/matched value/points for every matched rule) — not a live join, so history stays readable after a rule is edited or deleted.
- Malformed/unsupported rules (bad field, bad operator, invalid field/operator pairing) are **safely skipped and logged server-side** (`Log::warning`) — never break lead creation, editing, merge, or recalculation.
- `lead_score_computed_at` is maintained on every compute run (even a no-op one). The score write is a **raw query builder update**, never touching `updated_at` (see §2's architecture note).

**Scoring fields** (extensible registry, `App\Enums\LeadScoringField`): `priority`, `source_type`, `status`, `estimated_budget`, `deal_value`, `win_probability`, `has_email`, `has_phone`, `days_since_created`, `days_since_last_status_change`.

**Supported operators** (`App\Enums\LeadScoringOperator`): `>=`, `<=`, `>`, `<`, `=`, `!=`, `in`, `not_in` — each field's kind (numeric/enum/boolean) constrains which operators are valid, enforced both in the UI and server-side in `save()`.

**Trigger points** (`App\Services\LeadScoringService::SCORING_RELEVANT_DETAIL_FIELDS` is the single source of truth for which detail fields count):
- `LeadReceived` (new listener `RecomputeLeadScoreOnReceipt`)
- `CreateManualLead::handle()` (manual leads never fire `LeadReceived` — additive workaround, not a fix to that gap)
- `Show::updateStatus()` — status and/or priority changed
- `Show::applyDetailChanges()` — only when changed fields intersect `estimated_budget`, `deal_value`, `win_probability`, `email`, `phone`
- `LeadMergeService::merge()` — only when the merge's applied field resolutions intersect the same scoring-relevant set
- Daily `leads:recalculate-scores` sweep (scheduled, excludes merged-away leads) — the only thing that re-evaluates time-derived fields

**Deliberately does NOT trigger scoring**: assignment/unassignment, notes, attachments, generic `LeadUpdated` broadcasts, company-only edits, message-timeline appends, meeting/follow-up schedule/cancel/done actions.

**UI**:
- Score + per-rule breakdown shown on the Lead detail page and the Kanban flyout (`score-breakdown.blade.php`), read-only on view (never triggers a recompute itself).
- Manual "Recalculate" action, gated to Client Admin (`Show::canManageScoring`).
- Tenant-side Scoring Rules management page at `/leads/scoring-rules` (`App\Livewire\Tenant\LeadScoring\Index`), full CRUD, Client-Admin-only, with a soft warning callout when active rules could total over 100.
- The pre-existing hero stat box mislabeled "Lead Score" (it was actually `win_probability`) was corrected to **"Win Probability"** — `win_probability`'s own meaning/behavior/validation is completely unchanged, display label only.
- Priority remains a manual field; Score is a computed field — kept visually/conceptually distinct in the UI copy.
- **No manual score override** — out of scope for Phase 2a by explicit decision.

**Permissions**: no new permission slug — `App\Policies\LeadScoringRulePolicy` and `Show::canManageScoring` both reuse the existing `lead-management` `update` permission + `isClientAdmin()`. Tenant isolation enforced explicitly in every query (not relying on the `BelongsToTenant` trait alone, per §2).

**Explicitly deferred from Feature #2** (Phase 2b or later, not started): score badge in list/Kanban, score filtering, score sorting, dashboard/reporting, score-aware assignment (`LeadAssignmentService` was **not** made score-aware), ML/predictive scoring, workflow/nurturing integration, manual override, In-App Communication.

1. **Priority/SourceType value orientation bug**: `LeadScoringField::valueOptions()` built the Priority/SourceType dropdown as `[label() => value]` (e.g. `'High' => 'high'`), but `x-dropdown-select` treats the array key as the option's stored value and the array value as its display label — the opposite convention. 2. **Numeric Equals/NotEquals used lexicographic (string) comparison, not numeric comparison** — found while auditing bug #1's blast radius. `LeadScoringOperator::evaluate()`'s `=`/`!=` cases now branch to true numeric comparison when both operands are numeric, matching the four inequality operators' existing behavior; `normalize()` also gained a defensive array guard. 3. **Alpine/Livewire stale dropdown**: `x-dropdown-select` bakes its `options` array into Alpine's `x-data` once, at the DOM node's initial mount, and never re-evaluates it on a later Livewire morph of the same node. ## 7. Feature #3 — Lead Tagging

Final approved architecture and decisions (do not re-litigate without a real blocker):

- **Tenant-owned catalog, not Platform-Admin-managed**: `App\Models\LeadTag` (table `lead_tags`) carries `tenant_id` directly, like `LeadScoringRule` — deliberately NOT shaped like `LeadStatus`/`Currency`'s shared-catalog-plus-tenant-pivot pattern, since a tag is a tenant's own business-specific label with no cross-tenant consistency need. The same name/slug (e.g. "VIP") can exist independently in different tenants; `unique(tenant_id, slug)` is the only uniqueness constraint. No `BelongsToTenant` trait — every query filters `tenant_id` explicitly instead, same discipline as `LeadScoringRule`.
- **Attachment**: `Lead::tags()` is a `BelongsToMany` through the Laravel-default pivot table `lead_lead_tag` (no explicit table name needed), `withPivot('tagged_by')->withTimestamps()->orderBy('lead_tags.name')` — ordered by name for a stable chip-rendering order. `unique(lead_id, lead_tag_id)` on the pivot backs up the idempotent `syncWithoutDetaching()` attach path against duplicate rows.
- **Permissions — two-tier bar, no new `PermissionSlug`**: catalog CRUD (`App\Policies\LeadTagPolicy`) is Client-Admin-only (`isClientAdmin()` + `lead-management` `update`), the same bar as `LeadScoringRulePolicy`. Attach/detach on a specific lead reuses `LeadPolicy::update()` as-is (admin, or the lead's assigned Client User) — the same lightweight bar as adding a `LeadNote`, since tagging a lead you can already update is a day-to-day action, not catalog management.
- **Catalog management UI**: `/leads/tags` (`App\Livewire\Tenant\LeadTags\Index`), full CRUD, Client-Admin-only, mirrors the Scoring Rules page's shape exactly (create/edit modal, `x-confirm-modal` delete confirmation, `slugTaken` pre-check + `UniqueConstraintViolationException` catch for the race).
- **Attach/detach UI**: `App\Livewire\Tenant\Leads\Show::attachTag()`/`detachTag()`, a shared `partials/lead-tags-manager.blade.php` (tag chips + remove buttons + an "Add tag" picker limited to the tenant's existing catalog — **no inline tag creation** from the lead page by design) included from both the full-page `lead-hero.blade.php` and the Kanban flyout's `header.blade.php`. `attachTag()` re-verifies the selected tag's `tenant_id` server-side, never trusting the dropdown's rendered options alone.
- **Table/Kanban display**: a shared `partials/tag-chips.blade.php` renders up to 2 tag chips + a "+N" badge, included from both the Leads table (new 8th "Tags" column — `<colgroup>`/header/all row-shapes/skeleton updated in lockstep, percentages recomputed) and the Kanban card (`lead-card.blade.php`, additive block under `service_interest`, no flex/layout changes to existing elements). The Tags filter dropdown uses `icon="hashtag"`, deliberately not `icon="tag"` (already used, coincidentally, by the unrelated Source filter).
- **Filtering**: single-select "has this tag" added to `FiltersLeadsQuery` (`$tag` property, `tagOptions()`, one more `applyDropdownFilters()` branch using `whereHas('tags', ...)`) — shared by `Index` (both table and Client User Kanban board) the same way `$status`/`$priority` already are. Multi-tag AND/OR filtering is explicitly deferred, not built.
- **Activity logging**: `tag_added`/`tag_removed` reuse `LeadDetailUpdateLog`'s existing extensible `action` string mechanism (the same one `meeting_cancelled`/`followup_done`/`unassigned` already use) — `changed_fields => ['tag' => $tag->name]`, no new table. `Show::activity()` now includes `'fields' => $log->changed_fields` on every action-type event (harmless no-op for the pre-existing action types, which don't read it); `activity-card.blade.php` gained two matching `@elseif` branches.
- **Merge integration (Feature #1)**: `LeadMergeService::unionTags()` runs inside the merge's existing single transaction (no nested transaction) — every unique tag from both leads ends up on the survivor exactly once; a tag both leads already carried is never duplicated; a tag carried over from the loser keeps its original `tagged_by` attribution. Reads the loser's pivot rows via a plain `DB::table('lead_lead_tag')` select (not `$loser->tags`'s Eloquent pivot magic property) to keep this fully statically typed. Not added to `MERGEABLE_FIELDS` (not a scalar Lead column) or `CHILD_MODELS` (a tag definition isn't owned by either lead, only the attachment is) — it's its own explicit step.
- **Tag deletion**: deleting a tenant's tag (`LeadTags\Index::delete()`) detaches it from every lead that carried it via the pivot's `cascadeOnDelete` on `lead_tag_id` — no delete-when-in-use block, unlike `LeadStatus`/`Currency`, since this catalog is single-tenant with no cross-tenant referential risk to protect against. The delete confirmation modal shows the exact usage count first (`confirmingDeleteUsageCount`).

**Explicitly deferred from Feature #3** (not started): multi-tag AND/OR filtering, tag-based scoring (`LeadScoringField` untouched), tag analytics/reporting, bulk tag actions, CSV import/export for tags, inline tag creation from the Lead detail page.

## 8. Feature #4 — Deal / Opportunity (Phase 1)

Final approved architecture and decisions (do not re-litigate without a real blocker):

- **Many-to-one with Lead, not a Lead-field mirror**: `App\Models\Deal` (table `deals`) carries `tenant_id`/`lead_id` directly — a Lead may have any number of Deals over its lifetime (repeat business, an upsell, a lost deal followed by a fresh one). `Lead::deals(): HasMany`. No uniqueness constraint caps a Lead to one Deal.
- **Deal status is a plain 3-value PHP enum, deliberately not a catalog**: `App\Enums\DealStatus` (`Open`/`Won`/`Lost`) — NOT a tenant-configurable catalog like `LeadStatus`, and NOT reusing `LeadStatus` itself. Lead's own pipeline already models proposal_sent/negotiation/won/lost at the Lead level; Deal's status only ever answers "does this specific opportunity still need work" and is completely independent — a Deal status change never touches `Lead::status_id`, and vice versa. `DealStatus::canTransitionTo()` allows only `Open⇄Won` and `Open⇄Lost` — a direct `Won→Lost` or `Lost→Won` flip is blocked; reopening back to `Open` first is required, and every real transition (including reopen) writes a `DealStatusLog` row via `Show::changeDealStatus()`, which is the single entry point for every Deal status button (Mark Won/Mark Lost/Reopen all call it with a different target).
- **`DealStatusLog` is keyed by `deal_id` only** — never `lead_id`/`tenant_id`. This is why `LeadMergeService::CHILD_MODELS` gains `Deal::class` only, never `DealStatusLog::class`: a merge updates a Deal's `lead_id` but never its `id`, so every `DealStatusLog` row stays correctly attached to its Deal automatically, with zero reparenting code of its own. Do not add `DealStatusLog::class` to `CHILD_MODELS` — it would fail outright (that table has no `lead_id` column).
- **`Lead::currentDeal()` is a derived, non-persisted UI convenience only** — no `primary_deal_id`/`is_primary` column exists anywhere. It returns the most recently created **open** Deal if any exist, otherwise the most recently created Deal overall (a display fallback so the card isn't empty for a Lead whose only Deal already closed), with a deterministic `created_at` then `id` tiebreak. It never hides, deactivates, or subordinates any other Deal — every Deal stays fully visible/editable/reopenable in the Deal list regardless of what this returns.
- **Deal ownership is independent of Lead assignment**: `Deal.owner_id` defaults to `Lead.assigned_to` at creation time (a one-time copy, not a live sync) and is independently editable thereafter. A later Lead reassignment (`LeadAssignmentService::assign()`) never overwrites an existing Deal's `owner_id` — `LeadAssignmentService` itself was not touched by this feature at all.
- **Permissions — no new `PermissionSlug`, no new policy class**: every Deal action authorizes directly against the parent Lead via the existing `LeadPolicy`. Create/edit/close(Won)/close(Lost)/reopen all reuse `Gate::allows('update', $lead)` (admin, or the lead's assigned rep) — the same lightweight bar as adding a `LeadNote` or a Feature #3 tag. **Delete is the one exception**, gated `Gate::allows('delete', $lead)` (Client-Admin-only), matching the bar for deleting the whole Lead — removing a revenue record outright is treated as consequential.
- **Currency**: `Deal.currency_id` reuses the existing `Currency`/`tenant_currencies` catalog exactly as `Lead.deal_value_currency_id`/`estimated_budget_currency_id` already do (a currency without an amount means nothing — only persisted alongside a real `value`, same rule `Show::updateDeal()` already enforces). `Platform\LeadManagement\Settings::deleteCurrency()`'s in-use check was extended to also check `deals.currency_id` — this was a required correctness fix (not optional scope), since without it a currency referenced only by a Deal could be deleted out from under it.
- **Existing Lead commercial fields are completely untouched**: `deal_value`, `deal_value_currency_id`, `win_probability`, `estimated_budget`, `estimated_budget_currency_id` keep their exact current schema, validation, `LeadScoringField` behavior, `LeadMergeService::MERGEABLE_FIELDS` conflict-resolution, and UI — unchanged, for backward compatibility and Feature #2 (Lead Scoring) compatibility. No backfill, no mirroring, no deprecation in this phase. Any future reconciliation is its own separate, explicitly-approved decision.
- **UI is detail-page-first, Phase 1 only**: one new card (`partials/deals-card.blade.php`) on both the full Lead detail page (`show.blade.php`) and the Kanban flyout (`show-panel.blade.php`) — listing every Deal (open first, then closed, newest first within each group), with create/edit/status-change/delete actions inline. No new route, no Deal Kanban, no Deal table/list view, no Kanban-card/Leads-table surfacing of Deal data — all explicitly deferred (see below).
- **Activity logging**: Deal status transitions surface in `Show::activity()` as a new `deal_status_change` event type, queried directly against `DealStatusLog` (via `whereHas('deal', ...)`, one query regardless of how many Deals a Lead has) rather than looping each Deal's own `statusLogs()` — same "no N+1" discipline as every other `activity()` source. `activity-card.blade.php` gained one matching `@elseif` branch.

## 11. Feature #7 — CSV Import (+ Reverb Integration)

Final approved architecture and decisions (do not re-litigate without a real blocker). Full field-level detail (exact headers, size/row limits, duplicate-detection ordering, currency-code resolution, idempotency strategy) lives in `docs/lead-management/FEATURE-07-CSV-IMPORT-HANDOFF.md` — this section is the authoritative closure summary; that document is the detailed implementation reference.

**Core import architecture:**
- Max file size **10 MB**, max **10,000** data rows (header excluded), both enforced before anything is queued — the whole upload is rejected outright, never truncated.
- Exact allowed headers, case-insensitive/whitespace-trimmed: required `name`; optional `email`, `phone`, `company`, `industry`, `location`, `service_interest`, `budget`, `budget_currency`, `deal_value`, `deal_value_currency`, `status`, `priority`, `assignee_email`, `tags`. A missing `name` or any unknown column rejects the entire upload before a `LeadImport` row ever exists.
- Row-level failures are **partial-success** — one bad row fails on its own, every other valid row still imports.
- Duplicate detection: **existing-Lead** (normalized email OR phone, conflicting matches rejected) and **in-file** (first valid row wins, checked *before* the existing-Lead check so an in-file duplicate gets correct, distinct attribution) — never merges, never overwrites.
- Status/priority/assignee/tags/currency resolved **only** against the tenant's own catalogs — never auto-created; an unresolvable value fails only that row.
- Assignment goes through the real `LeadAssignmentService::assign()` (real notification); `autoAssign()`/round-robin is never invoked. Scoring is explicit via `LeadScoringService::computeFor($lead, 'lead_received')`, synchronous per row.
- `LeadReceived`/`LeadUpdated` **never** fire for a CSV-imported row (avoids per-row notification/auto-assignment fan-out at import scale) — this is why the import's own live-status mechanism (below) had to be built independently rather than riding on those events.
- Processing is queued and chunked via Laravel Excel's native `ShouldQueue` + `WithChunkReading` (chunk size 200) — real Laravel job **chaining**, never `Bus::batch()`. Chunks run strictly sequentially, guaranteeing deterministic row-order with no lock.
- Uploaded CSVs stored on **private** local storage, private path never rendered in either Blade view.
- `App\Models\LeadImport`/`LeadImportRow` persist accurate per-row outcomes and a terminal status (`Completed`/`CompletedWithErrors`/`Failed`).
- New lazily-provisioned `LeadSourceType::CsvImport` (structurally identical to `Manual`), required a companion Postgres CHECK-constraint migration (`lead_sources.type`) — the same established pattern every prior `LeadSourceType` addition has needed.
- No scope creep: no field-mapping UI, no new permission slug (reuses `Gate::authorize('create', Lead::class)` — the same bar as manual Lead creation), no Deal/Task creation from import.
- Navigation: an **"Import Leads" button was added to `/leads`** (Client Admin table view only, next to "Export CSV", gated by `canCreateLead`) at the user's explicit request — the Scoring Rules/Tags-style "URL-only, no nav entry" precedent noted during initial build was superseded for this feature specifically; the Kanban (Client User) view was deliberately left unchanged.

**Real-time status architecture (Reverb primary + one-time reconciliation, added during browser QA remediation — see bugs below):**
- `App\Events\LeadImportStatusChanged` — `ShouldBroadcast` + `ShouldDispatchAfterCommit` (defensive; verified against actual Laravel Excel source that neither firing point currently sits inside a wrapping transaction, so this is a no-op today and protects only against a future refactor), deliberately never `ShouldBroadcastNow` (finalization must never block on Reverb being reachable).
- Fires at **exactly the two existing terminal finalization points** in `App\Imports\LeadCsvImport` — the `AfterImport` listener (normal completion) and `failed(Throwable $e)` (chain-aborting infrastructure fault) — never per-row, never on the Pending→Processing transition.
- `PrivateChannel('lead-import.{id}')`, authorized in `routes/channels.php` with the same bar as `Show::mount()`: `$user->tenant_id === $leadImport->tenant_id && Gate::forUser($user)->allows('create', Lead::class)`.
- `broadcastWith()` carries **only** `['id' => $leadImport->id]` — `App\Livewire\Tenant\LeadImports\Show::getListeners()` (`echo-private:lead-import.{id},.lead-import.status-changed` → `refreshStatus()`) always re-queries authoritative DB state rather than trusting the payload, matching every other Echo listener in this app (`NotificationBell`, `Leads\Index`).
- **No recurring polling of any kind.** A single **one-time reconciliation** — `x-data` + `x-init="setTimeout(() => $wire.refreshStatus(), 5000)"` on the Show page's root element, inside the same non-terminal `@if` guard the old poll used — fires exactly once, 5s after mount, to close two narrow races Reverb alone can't: the terminal broadcast landing before this page's private-channel subscription finishes, or a brief Reverb disconnect exactly during finalization. It never re-arms; after it fires, Reverb is the sole remaining mechanism for that import. This is a plain Alpine `setTimeout`, not Livewire's `wire:poll` machinery, so it is not subject to that directive's background-tab throttle (see bugs below).

**Bugs found and fixed during browser QA (in the order encountered):**

2. **Status badge stuck on "Processing" until a manual refresh**, even though the backend finalized correctly in ~2s every time. Root cause, confirmed by reading Livewire's actual compiled JS (`wire-poll.js`): `wire:poll` has a built-in throttle that skips ~95% of ticks while `document.hidden` is true, and the original `wire:poll.3s="refreshStatus"` lacked the `.keep-alive` modifier needed to opt out. The MCP/CDP-automated browser QA session effectively backgrounded the tab for most of the wait, so polling was throttled to roughly one tick per ~60s rather than genuinely broken. **`wire:navigate` was explicitly investigated and ruled out** (verified in source: `nowInitializeAlpineOnTheNewPage()` correctly re-scans directives after every navigate swap). This finding is what drove the deliberate architecture decision to move to Reverb-primary + one-time reconciliation (above) rather than just adding `.keep-alive` to a recurring poll.
3. Two smaller bugs from the pre-Reverb final verification pass, both fixed and re-verified: a missing Postgres CHECK-constraint migration for `csv_import` (production-blocking on Postgres, invisible on SQLite's test driver), and test-only `Storage::fake('local')` omissions that had been leaking real files into `storage/app/private/lead-imports`.

- **A reopened lead keeps its original response time** — `first_contacted_at` is never reset by this feature (nothing in this feature writes to that column at all); the existing `?? now()` idempotency guard in `Show::updateStatus()`/`Index.php`'s bulk equivalents is what already guarantees this in production, verified here by a regression test.

No new route, no new sidebar entry — same page, same URL as Feature #8.

- **Tenant-owned catalog, not Platform-Admin-managed** — same shape as `LeadTag`/`LeadScoringRule`: `tenant_id` stored directly, no `BelongsToTenant` trait, every query filters `tenant_id` explicitly. `lead_custom_field_values` also carries `tenant_id` directly (same discipline as `LeadDuplicateLink`/`Deal`/`Task`), `unique(lead_id, lead_custom_field_definition_id)`, and the definition FK is `restrictOnDelete`.
- **Fixed Phase 1 type set** — `App\Enums\LeadCustomFieldType`: `text`, `number`, `date`, `select` only (no multi-select/checkbox). Each type owns its own `validationRules(required, options)`; `LeadCustomFieldDefinition::validationRules()` just applies a definition's own live `is_required`/`options` to its own type. This is the single source of truth both the manual-create form and the Lead detail/flyout edit form validate against.
- **Client Admin catalog CRUD** at `/leads/custom-fields` (route name `tenant-leads.custom-fields`, `App\Livewire\Tenant\LeadCustomFields\Index`), gated by a new `App\Policies\LeadCustomFieldDefinitionPolicy` that — like `LeadTagPolicy`/`LeadScoringRulePolicy` before it — reuses the existing `lead-management` `update` permission + `isClientAdmin()`. **No new `PermissionSlug`.** A sidebar entry ("Custom Fields") was added alongside the existing "Lead Sources"/"Reports & Analytics" items, following Feature #8's own precedent for adding a nav entry to a standalone Lead Management sub-page. Machine `key` is auto-slugged from `name` (`LeadTag`-style), tenant-scoped unique, with the same pre-check + `UniqueConstraintViolationException` race-catch every sibling catalog page uses.
- **Required-field semantics are explicitly non-retroactive**: `is_required` is only ever asserted inside a create/edit submission's own dynamically-built validation rules, assembled fresh from the tenant's currently-active definitions at submit time. No migration, cron, or lazy check ever walks existing leads to flag them invalid, and marking a field required later never blocks editing an unrelated field on a lead that has no value for it.
- **Type/options immutability** — once any `LeadCustomFieldValue` row exists for a definition, its `type` and `options` become permanently locked (blocked with a validation error in `LeadCustomFields\Index::save()`); `name`/`is_required`/`sort_order`/`is_active` stay freely editable regardless. There is no safe, defined reinterpretation of existing typed data across a type change, so this is blocked outright rather than silently transformed or discarded.
- **Field lifecycle**: deactivating (`is_active = false`) hides a field from future create/edit forms but leaves its already-captured values fully visible, read-only, on any lead that has one (`Show::customFieldDisplayRows()` unions active definitions with any inactive-but-still-valued one) — fully reversible via reactivation. Deleting a definition is **blocked outright while any value exists** (the `LeadStatus`/`Currency` "refuse, don't cascade" pattern, not `LeadTag`'s cascade pattern), with the delete-confirmation modal showing the exact usage count first; deleting an unused definition is a plain hard delete.
- **Lead create/edit integration**: a new `App\Actions\Tenant\SaveLeadCustomFieldValues` action is the single validate-against-current-active-definitions/diff/upsert-or-delete primitive shared by both `Leads\Index::saveLead()` (manual creation) and `Leads\Show::updateCustomFields()` (detail/flyout edit) — never duplicated logic across the two paths. A submitted definition id that doesn't belong to the current tenant, or that isn't currently active, is silently ignored, never written — the action re-derives the real definition set from the database rather than trusting the caller's keys. A blank submitted value **deletes** the value row rather than storing an empty string.
- **UI placement**: a new "Custom Fields" card (`partials/custom-fields-card.blade.php`) on both the full Lead detail page (`show.blade.php`) and the Kanban flyout (`show-panel.blade.php`), mirroring the Deals/Tasks/Notes cards' dual-surface inclusion exactly. **Deliberately absent from the Kanban card and the Leads table** — same "detail-page/flyout only, not card/table" precedent Feature #1's duplicate badge already established, avoiding an undefined "compact display of N arbitrary tenant-defined fields" UX.
- **Audit logging reuses `LeadDetailUpdateLog` as-is — no new history table.** `SaveLeadCustomFieldValues` returns the human-readable **names** (not raw definition ids/keys) of whatever fields actually changed; the caller writes exactly one log entry per save containing only those names, or none at all on a true no-op (diff-based, same discipline as `applyDetailChanges()`).
- **Merge integration (Feature #1) is a separate, bespoke step — custom field values are in neither `MERGEABLE_FIELDS` nor `CHILD_MODELS`**, and the existing scalar-field merge logic in `LeadMergeService` was not modified at all. Two new methods: `conflictingCustomFieldValues()` (namespaced `custom_field:{definitionId}` keys, mergeable into the same `$conflicts`/`field_resolutions` array `conflictingFields()` already populates, so `Show`'s existing merge modal needed zero template changes — only `mergeFieldLabel()`/`mergeFieldValueLabel()` gained a `custom_field:` branch to resolve a tenant-defined name live from the catalog) and `autoFillCustomFieldValues()`. Approved behavior, a deliberate and scoped divergence from `conflictingFields()`'s own scalar-field default: **survivor blank + loser has a value → auto-copied directly, never surfaced as a conflict; both have different non-blank values → explicit conflict in the existing modal, defaulting to keep-survivor, admin may choose loser.** Equal or both-blank values are a no-op. The loser's own value rows are never reparented (same reasoning as Tags' `unionTags()` needing its own bespoke step) — they simply remain attached to the retired, never-hard-deleted loser lead, fully queryable.

**Explicitly deferred from Feature #11 Phase 1** (not started): CSV import support for custom fields, bulk custom-field editing, custom-field filtering/search/sorting, reporting/dashboard breakdowns, webhook custom-field ingestion, Website Form integration, multi-select/checkbox field types, field-level (per-field) permissions, retroactive backfill of existing leads, any historical value-change timeline beyond the single `LeadDetailUpdateLog` entry per save, and a generic dynamic-form engine.

## 17. Feature #13 — Website Form Builder (Phase 1)

Final approved architecture and decisions (do not re-litigate without a real blocker):

- **Multi-form from the start — no single-form-per-tenant assumption.** `App\Models\WebsiteForm` (table `website_forms`) is a tenant-owned catalog entry, same shape as `LeadTag`/`LeadScoringRule`/`LeadCustomFieldDefinition`/`LeadSourceCost`: direct `tenant_id`, no `BelongsToTenant`, every query filters `tenant_id` explicitly. A tenant may create any number of forms.
- **One shared, lazily-created `LeadSource` per tenant** (`type = WebsiteForm`) backs every `WebsiteForm` a tenant creates — `WebsiteForms\Index::save()` does a `firstOrCreate()` on first form creation and reuses that same row (including a tenant's pre-existing legacy Website Form source, if one already exists) for every subsequent form. Per-form reporting is explicitly deferred to a future phase; `website_form_id`/`website_form_name` are captured in each Lead's `source_data` snapshot now so that future reporting doesn't need a schema change.
- **Form-specific fields are a separate table, not a JSON column** — `App\Models\WebsiteFormField` (table `website_form_fields`) is one row per field a specific form accepts: either a fixed Lead column (`fixed_field`, one of `email`/`phone`/`message` — `name` is always implicit and required, never has its own row) or a reference to an existing `LeadCustomFieldDefinition`. `restrictOnDelete` on the custom-field FK, `cascadeOnDelete` on the parent-form FK (a field-configuration row is not data, so it's safe to cascade when its form is deleted). Two unique constraints prevent attaching the same fixed field or the same custom field twice to one form.
- **Per-form high-entropy token, hashed at rest** — `Str::random(40)` (the same convention Sanctum's own personal access tokens use), SHA-256 hashed into `token_hash` (unique). The plaintext is shown to the admin exactly once, in a dedicated modal, at creation time and again on regeneration — never persisted, never re-displayable afterward. Regeneration is a plain hash replacement with no grace period: the old token stops working immediately, proven end-to-end by a real two-request test (old token 404s, new token works, right after regenerating).
- **New public submission endpoint, separate from and non-disruptive to the legacy webhook** — `POST /api/webhook/website-form/{tenant_code}/{form_token}` (`LeadWebhookController::websiteFormSubmit()`), authenticated purely by the token (resolved via `resolveWebsiteForm()`, which independently checks tenant-active, form-active, and tenant-ownership, all folding into an identical 404 so a probing request learns nothing about which check failed). The pre-existing `POST /api/webhook/website-form/{tenant_code}` (`websiteForm()`, API-key-authenticated) was not modified in any way — confirmed by direct code diff, not just by its tests still passing. `createLead()` (the one shared "create Lead + fire `LeadReceived`" helper used by all 5 pre-existing ingestion channels) gained one new optional parameter, default `[]`, so every existing call site's behavior is provably unchanged.
- **The server derives everything; the client controls nothing** — `App\Actions\Tenant\ValidateWebsiteFormSubmission` builds its validation rules and accepted-field set entirely from the token-resolved `WebsiteForm`'s own `WebsiteFormField` rows, never from the POST body's shape. A submitted key that isn't part of that specific form's own configuration (including another of the same tenant's forms' fields) is silently discarded, not stored, not erroring — a deliberate divergence from the legacy endpoint's "keep every extra field" behavior. Custom field values are additionally re-validated a second time by the unmodified, pre-existing `SaveLeadCustomFieldValues` action, which independently re-derives the tenant's own active definitions rather than trusting any caller's keys — two independent layers, neither trusting client input.
- **Existing Custom Field system (Feature #11) is reused as-is, not duplicated.** A form can expose any of the tenant's own custom field definitions; a definition later deactivated is silently skipped in a submission (not a hard failure) without blocking the rest of the fields; a definition still referenced by any `WebsiteFormField` cannot be deleted (`LeadCustomFieldDefinition::isReferencedByWebsiteForm()`, a new additive guard in the pre-existing `LeadCustomFields\Index::delete()`, mirroring the exact `hasValues()` precedent already there) — no orphaned field configuration is reachable.
- **Honeypot, no CAPTCHA** — a fixed hidden field (`_gotcha`); a non-empty value returns the identical `200 {"status":"ok"}` a real success would (never tipping off a bot) but creates nothing. CAPTCHA was explicitly excluded from Phase 1 scope.
- **Two-tier rate limiting — the first rate limiting on any public webhook route in this codebase.** `AppServiceProvider::configureRateLimiting()` registers `website-form-per-form` (20/min, keyed by token+IP) and `website-form-per-tenant` (60/min, keyed by tenant_code+IP), applied to the new route as **two separate** `throttle:` middleware entries — a real, non-obvious Laravel trap was hit and fixed here: `throttle:name1,name2` (comma-joined in a single middleware string) does **not** register two named limiters, it's parsed as two positional `$maxAttempts`/`$decayMinutes` arguments instead, silently breaking with a `MissingRateLimiterException` at request time despite both limiters being correctly registered. The legacy endpoint deliberately received no new rate limiting.
- **No hosted forms, no public form page, no iframe, no JS embed SDK.** This app never renders or serves the form itself — the tenant's own developer builds the HTML and POSTs to the form's endpoint. The one UI addition beyond plain CRUD is a read-only "Integration Details" panel (endpoint URL, accepted field keys, which are required, an example JSON payload) — documentation only, not a hosted schema/public endpoint.
- **Authorization — no new `PermissionSlug`.** `App\Policies\WebsiteFormPolicy` reuses the existing `lead-management` `update` permission + `isClientAdmin()`, the identical bar `LeadTagPolicy`/`LeadScoringRulePolicy`/`LeadCustomFieldDefinitionPolicy`/`LeadSourceCostPolicy` already use. The public submission endpoint correctly carries no authenticated-authorization check at all — the token is its sole credential, by design.
- **Admin UI**: `/leads/website-forms` (`App\Livewire\Tenant\WebsiteForms\Index`), full CRUD (create/edit/activate-deactivate/delete/configure-fields/regenerate-token) plus the Integration Details panel, following the same Livewire catalog pattern as every sibling page. Deleting a form is unconditionally allowed — a `WebsiteForm` has no hard FK from `Lead` (attribution is a `source_data` snapshot only), so deletion never touches any existing Lead, proven by a dedicated test.

**Explicitly deferred from Feature #13 Phase 1** (not started): hosted/public forms, iframe embedding, a JS embed SDK, a drag-and-drop field builder, conditional field logic, multi-step forms, file uploads, CAPTCHA, advanced spam scoring beyond the basic honeypot, per-form analytics/conversion reporting, A/B testing, multi-language forms, campaign-specific forms, email automation, advanced workflow automation, webhook delivery retries, advanced styling/theming, and any per-domain allowlisting on the new builder endpoint (the token is the primary security boundary in Phase 1).

## 18. Feature #14 — Consent / GDPR (Phase 1)

Final approved architecture and decisions (do not re-litigate without a real blocker):

- **Dedicated, structured consent architecture — not Lead columns, not a Custom Field.** Two new tables: `lead_consents` holds the CURRENT effective state, one row per `(lead_id, consent_type)` (`unique` constraint), upserted on every grant/withdraw; `lead_consent_events` is the permanent, append-only history — one row per action, never updated or deleted by any code path in this app (same "immutable in practice" convention `LeadStatusLog`/`LeadScoreLog` already follow). Both tables carry `tenant_id` directly, `cascadeOnDelete` on `lead_id`, no `BelongsToTenant` reliance.
- **Two independently tracked consent types, `App\Enums\ConsentType`** (`Privacy`/Data-Processing, `Marketing`/Communication) — a plain, engineering-controlled PHP enum (matching `DealStatus`/`TaskStatus`/`WebsiteFormFieldType`'s precedent), not a tenant-configurable catalog. Terms Acceptance was explicitly **not** added as a third type in Phase 1.
- **Status model — `Granted`/`Withdrawn` only; "Not Provided" is the absence of a row**, never a third status value — the same "no row and blank are the same state" discipline `LeadCustomFieldValue` already established.
- **`App\Actions\Tenant\RecordLeadConsent`** is the single grant/withdraw primitive every caller goes through — one `DB::transaction()` per call that upserts the current-state row and appends exactly one history event together, never partially.
- **Website Form Builder integration**: a new `WebsiteFormFieldType::Consent` case (alongside Fixed/Custom), with `consent_type`/`is_required`/`policy_version`/`policy_url` columns on `website_form_fields`, configured per form in `WebsiteForms\Index`'s existing modal. `App\Actions\Tenant\ValidateWebsiteFormSubmission` derives every consent field's type/required-ness/policy metadata entirely from that form's own stored configuration — never from the request. Checkbox semantics: optional + omitted/false → no record (stays Not Provided); required + omitted/false → 422; a present, non-boolean-ish value → 422; an explicit true → a grant, recorded via `RecordLeadConsent` immediately after `createLead()` in `LeadWebhookController::websiteFormSubmit()`, snapshotting the same `website_form_id`/`website_form_name` already used for `source_data`, plus `ip_address`/`user_agent`. An unconfigured or cross-form consent key is silently discarded, exactly like every other Feature #13 field type.
- **Manual Lead management**: a new "Consent" card on the Lead detail page and Kanban flyout (`App\Livewire\Tenant\Leads\Show::grantConsent()`/`withdrawConsent()`) shows both types' current status, last-changed timestamp/source, and inline history. **No new `PermissionSlug`, no dedicated `LeadConsentPolicy`** — both actions reuse the existing `Gate::allows('update', $lead)` bar, the same lightweight authorization every other lead-child action (notes, tags, custom fields) already uses; withdrawal deliberately is **not** gated behind the stricter `delete` permission.
- **Audit/activity integration**: `Leads\Show::activity()` gained a `consent_change` branch sourced from `LeadConsentEvent`, rendered in `activity-card.blade.php` alongside every other event type — manual events attribute the acting `TenantUser`; Website Form and merge-synthetic events correctly show no user, with the form name or "Lead Merge" shown instead.
- **Lead merge — conservative, Withdrawn always wins, nothing ever lost**: `LeadConsentEvent` (history) is a plain `CHILD_MODELS` reparent (both leads' full histories preserved on the survivor, no dedup needed — it's append-only). `LeadConsent` (current state) gets bespoke handling in `LeadMergeService::mergeConsents()`, since its unique constraint rules out a blind reparent: either side `Withdrawn` → survivor ends `Withdrawn` (never silently downgraded back to `Granted`); both `Granted` → stays `Granted`; only one side has a record → copied onto the survivor; neither side has one → stays Not Provided. A synthetic `source = Merge` event is written for every type where at least one side had a record, even when nothing changed, documenting the merge outcome.
- **Legacy Website Form webhook (`POST /api/webhook/website-form/{tenant_code}`) is completely unchanged** — confirmed by direct code diff, not just by its existing tests re-passing unmodified. No reinterpretation of arbitrary `source_data` as consent was built.
- **External platform consent normalization explicitly deferred** — Facebook Lead Ads, Facebook Messenger, Instagram, WhatsApp, and LinkedIn Lead Gen were not modified; any platform-native consent/opt-in field they carry remains unread, exactly as before this feature. ## 19. Feature #15 — In-App Communication (Phase 1)

Final approved architecture and decisions (do not re-litigate without a real blocker):

- **Normalized `conversations` + `messages` tables, no `message_status_events` table.** `conversations` — one row per `(tenant_id, lead_source_id, channel, external_thread_id)`, `channel` ∈ {`whatsapp`, `messenger`, `instagram`} (a small, engineering-controlled enum, not a reuse of `LeadSourceType`), `external_thread_id` is the platform's own opaque thread identifier (WhatsApp: phone number; Messenger: PSID; Instagram: IGSID — deliberately never assumed to share a shape). `messages` — one row per inbound or outbound message, `unique(tenant_id, channel, external_message_id)` (nullable-safe), `status`/`status_updated_at`/`failure_reason` meaningful only for `direction = outbound`.
- **Additive inbound dual-write, no historical backfill.** `App\Actions\Tenant\RecordInboundMessage` runs alongside — never instead of — the existing `Lead.source_data` JSON append in all three inbound webhook handlers (`LeadWebhookController::facebookMessenger()`/`instagram()`/`whatsapp()`, both the new-lead and follow-up-append paths). The legacy JSON write is byte-for-byte unchanged; confirmed by every pre-existing webhook test passing unmodified. `Lead::messageTimeline()` was extended, not rewritten, to also surface normalized rows.
- **`Lead::messageTimeline()` backward-compatibility fix (found and corrected during Final Verification, before closure — not a pre-existing bug, a defect in this feature's own first implementation).** An initial version switched to normalized rows exclusively the moment ANY existed for a lead, which silently hid a lead's entire pre-existing legacy message history the instant it received its first post-cutover inbound message — reproduced directly during audit (a lead with 2 legacy messages showed only 1 entry after one new inbound message arrived). Corrected to a per-*entry* boundary: a legacy JSON entry is shown only if it is strictly older than this lead's own first dual-written inbound message; every normalized row (inbound after cutover, plus every outbound reply) is always shown. A lead with no dual-written messages yet keeps its full legacy timeline untouched. Two regression tests added reproducing the exact failure and proving outbound messages render correctly alongside legacy history.
- **Outbound sending — WhatsApp, Messenger, Instagram, free-form only.** `App\Contracts\MessageSenderInterface` + `WhatsAppSender`/`MessengerSender`/`InstagramSender`, resolved via a plain `match()` factory (`MessageSenderFactory`), matching this module's existing "one enum, one match() per case" convention rather than a container-tag abstraction with no precedent here. Credentials are read fresh from `$conversation->leadSource->config` at send time, every time — never cached, never placed in a queued job payload (verified: `SendOutboundMessage`/`ReconcileOutboundMessageStatus` use `Illuminate\Foundation\Queue\Queueable`, which includes `SerializesModels` — jobs carry only a model reference, re-fetched from the database on execution). Recipient and channel are always server-derived from the resolved `Conversation`, never trusted from client input. `InstagramSender` reuses the exact existing `auth_mode`-based host branching (`graph.instagram.com` vs `graph.facebook.com`) `LeadWebhookController::fetchInstagramProfile()` already established — verified against the actual code, not assumed, and proven by a dedicated test per branch. No templates, no Human Agent tag, no Message Tags, no business-initiated/proactive messaging — a reply within the standard messaging window only.
- **`App\Services\OutboundEligibilityService`** is the single gate every send goes through, evaluated both at compose-time (UI state) and again, redundantly, inside the queued send job itself: lead not merged away; Privacy consent (Feature #14) not `Withdrawn` (blocks ALL outbound, not just marketing — a deliberate conservative safety rail); source active with required credentials present; the channel's own 24-hour messaging window (`MessageChannel::windowHours()`, a named per-channel constant, verified independently per platform — Messenger's general Message Tags feature was in fact deprecated by Meta globally as of February 2026, leaving even less post-window capability than originally scoped, reinforcing that "within-window reply only" is the correct Phase 1 boundary) still open. **Marketing consent is deliberately NOT checked** — a direct within-window reply to a customer-initiated conversation is service/transactional, not marketing; proven by a dedicated test that a withdrawn Marketing consent alone never blocks a service reply.
- **Queued outbound sending with same-row updates.** `Show::sendMessage()`/`resendMessage()` create a `status = pending` `Message` row synchronously, then dispatch `SendOutboundMessage` (`tries = 3`, backoff `[5, 15, 30]`s) — the job only ever updates that one row, never creates a second, making retry safe. A transient infrastructure/network failure may retry at the job level; a confirmed platform rejection (`SendResult::failure()`) marks the message `failed` immediately with no further attempt — manual resend only, always a brand-new `Message` row, the original failed row left untouched as a permanent record. A short `Cache::lock` (mirroring `LeadWebhookController::withDedupeLock()`'s existing idiom), keyed by conversation + a hash of the exact body, blocks a double-click/duplicate submission.
- **Status reconciliation is additive to the existing webhooks, always ACKs 200, and is channel-specific.** New `foreach` branches inside the existing `facebookMessenger()`/`instagram()`/`whatsapp()` methods (never a new route) dispatch `App\Jobs\ReconcileOutboundMessageStatus` rather than updating inline — preserving the pre-existing "always acknowledge 200" policy those methods already documented. WhatsApp correlates reliably by `external_message_id` (wamid); Messenger/Instagram correlate primarily by conversation + watermark timestamp (Meta's own delivery/read webhook's `mids` array is documented as sometimes absent — verified via live documentation research, not assumed), using `mids` opportunistically when present. Status updates are strictly monotonic (`MessageStatus::rank()`) and never touch an inbound row.
- **Concurrency fix (found and corrected during Final Verification, before closure).** `ReconcileOutboundMessageStatus::applyStatus()` originally read an already-loaded `Message` and wrote via a plain `->update()` with no lock — two genuinely concurrent status webhooks for the same message (e.g. "delivered" immediately followed by "read", processed by two queue workers) could both read the same pre-update status and, depending on write order, downgrade the row. Fixed by re-fetching the row inside `DB::transaction()` with `lockForUpdate()`, making the read-check-write atomic per message — the same locking idiom Feature #12's `LeadSourceCost` concurrency fix already established for this codebase.
- **A not-yet-found WhatsApp status lookup retries via the job queue rather than being silently dropped** — the target `Message` row is always created before any send attempt, so a genuine "not found" almost always means a narrow timing race, not a permanently missing message; only after all retry attempts are exhausted is an operator-visible warning logged.
- **Lead-detail/Kanban-flyout composer only — no unified inbox.** One new card (`message-composer-card.blade.php`), visible only for a WhatsApp/Messenger/Instagram-sourced lead, gated by the existing `LeadPolicy::update()` (no new `PermissionSlug`, no dedicated policy class), showing live eligibility state, a text-only composer, and outbound message history with status badges and manual resend on a failed message.
- **Reuses the existing `LeadUpdated`/Reverb infrastructure exactly** — every outbound state change (created, sent, failed, delivered, read) fires the same pre-existing `LeadUpdated` event on the same pre-existing `tenant.{id}`/`lead.{id}` private channels; no new broadcast event or channel was created.
- **Rate limiting — approved numbers, adapted mechanism.** 30 outbound sends/user/minute and 100/tenant/minute, enforced via direct `RateLimiter::tooManyAttempts()`/`hit()` calls inside `Leads\Show::passesOutboundRateLimits()` (called from both `sendMessage()` and `resendMessage()`, before any `Message` row is created) rather than through `AppServiceProvider`-registered `RateLimiter::for()` + route `throttle:` middleware — an accepted, explicitly-approved architectural variation, since a Livewire component action has no natural attachment point for route-level middleware the way Feature #13's public webhook endpoint did. Both limits use the same underlying `Illuminate\Cache\RateLimiter`, both keys are scoped to already-authenticated/authorized context (never client input), and both methods are covered consistently.
- **Tenant isolation / security**: every new query chain terminates at an already-tenant-verified parent — `Conversation`/`Message` access always flows through `$this->lead`'s own relations (itself gated by `LeadPolicy::view()`/`update()` at `Show::mount()`), never a bare model lookup; `ReconcileOutboundMessageStatus` filters by `tenant_id` first in every query; credentials are never logged, never serialized into a queue payload, and always re-read fresh from `LeadSource.config` at send time. `MetaPermissionsController::REQUIRED_SCOPES` gained `whatsapp_business_messaging` alongside the existing `pages_messaging`/`instagram_manage_messages`, verified via live Meta documentation research to be the correct, checkable scope for WhatsApp Cloud API sending (an earlier assumption that WhatsApp had no checkable scope was corrected during the Final Architecture Validation pass, before implementation).

**Explicitly deferred from Feature #15 Phase 1** (not started): WhatsApp/Messenger/Instagram template messages and template management, Messenger's `HUMAN_AGENT`/Message Tags extended-window messaging (and Instagram's equivalent), business-initiated/proactive/marketing messaging (and the `ConsentType::Marketing` enforcement it would require), a unified cross-lead inbox, campaign/bulk/broadcast messaging, marketing automation, scheduled campaigns, a media/file/attachment composer for outbound (inbound attachment handling is untouched), voice/video calling, AI auto-replies/chatbot behavior, A/B testing, analytics dashboards for messaging, advanced conversation assignment/routing, a customer-facing portal, email channels, automatic retry of a confirmed platform send failure, live per-status-transition broadcast granularity beyond the existing full-lead `LeadUpdated` refresh, and any live pre-send Meta scope-validity check (scope readiness is checkable via the existing, now three-scope, `MetaPermissionsController` tool, but is not automated or surfaced in the compose UI itself).

### C5 — Raw Meta access token serialized into DownloadLeadAttachment's queued job payload — **COMPLETE / APPROVED / CLOSED**

**Finding**: `App\Jobs\DownloadLeadAttachment` took the Meta access token (and, for WhatsApp, the `phone_number_id`) as plain constructor scalars — neither intercepted by `SerializesModels`, so both were serialized in cleartext into the `jobs` table (queue driver: `database`) and, since the job's `$tries = 1`, permanently into `failed_jobs.payload` on any failure. This contradicted the "resolve credentials fresh inside the job, never pass them through `dispatch()`" convention already established elsewhere in this module (`WhatsAppSender`, `SendOutboundMessage`, `ReconcileOutboundMessageStatus`, `ProcessEmailLeadSource`).

**Fix**: Removed `accessToken`/`whatsappPhoneNumberId` from the job's constructor entirely. Added a private `resolveCredentials()` method that re-reads `$this->attachment->lead->source->config` at execution time — mirroring `WhatsAppSender::send()`'s existing pattern exactly. `LeadWebhookController::createPendingAttachmentAndDispatch()` no longer passes either value into `dispatch()`; its pre-dispatch token-existence guard is unchanged. If credentials can't be resolved at execution time (e.g. config cleared between dispatch and execution), the job now calls the existing `markFailed()` with a clear reason rather than crashing — the same visible-`Failed`-attachment outcome shape every other failure path in this job already produces.

**Scope deviation, explicitly approved during implementation**: `tests/Feature/Leads/WebhookAttachmentTest.php` (not in the original approved file list) had 3 assertions directly referencing the removed `accessToken`/`whatsappPhoneNumberId` properties — a direct, unavoidable mechanical consequence of the constructor change, not an independent scope expansion. Implementation stopped and reported this before touching the file; the fix (replacing the value comparisons with `! property_exists($job, 'accessToken')`/`! property_exists($job, 'whatsappPhoneNumberId')` negative assertions) was explicitly approved before proceeding.
