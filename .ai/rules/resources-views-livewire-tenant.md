# Resources Views Livewire Tenant

## Mobile card stack must mirror the desktop table's Lead ID treatment (shimmer + non-muted color)
The Client Admin leads view renders two separate markup blocks for the same $this->leads collection — a `sm:hidden` mobile card stack and a `hidden sm:block` desktop table — both always rendered server-side, with CSS (not a conditional) picking which one shows. The mobile card's Lead ID used to be hardcoded muted (`text-zinc-400 dark:text-zinc-500`) with no shimmer logic at all, while the desktop table computed `$rowHasActiveAlert` (meeting/follow-up alert window) per row and applied `.lead-id-shimmer-text` + a tooltip when active, falling back to a still-somewhat-muted `text-zinc-500 dark:text-zinc-400` otherwise. Fixed: the mobile `@foreach` now also computes `$cardMeetingAlertActive`/`$cardFollowUpAlertActive`/`$cardHasActiveAlert` and renders the identical shimmer+tooltip block when active, or `text-zinc-700 dark:text-zinc-300` (not muted) otherwise. Any future change to the desktop table's per-row alert/Lead ID treatment must be mirrored into the mobile card block too — they're two independent copies of the same markup, not a shared partial, so nothing enforces this beyond remembering to update both.

## Mobile lead card is itself the click target — no View/Delete buttons
The mobile card stack's footer used to have View (→ tenant-leads.show) and Delete (confirmDeleteLead) buttons. Removed both to keep the card compact — the card's root element is now a real `<a href="{{ route('tenant-leads.show', $lead) }}" wire:navigate>` instead of a `<div>`, so tapping anywhere on the card opens the lead. Delete is still reachable from the lead's own Show page (Show::canDelete()/confirmDelete()), which already has its own delete action — nothing was actually removed, just relocated off this card. Used a real `<a>` wrapping the whole card rather than a stretched absolute-overlay anchor (the pattern used in NotificationBell) because there's no other interactive element left inside the card to layer above — the shimmering Lead ID's `flux:tooltip` renders a `<ui-tooltip>` web component, not a link/button, so nesting it inside `<a>` is valid and its hover/focus behavior is unaffected. Don't add a new interactive element (a button, a nested link) into this card without switching back to the overlay pattern first — a real `<button>`/`<a>` nested inside this outer `<a>` would be invalid HTML and clicks on it would still trigger the card's own navigation. The desktop table (a separate markup block, not shared) keeps its own row-level View/Delete actions unchanged.

## Mobile Facebook Lead Ads source card: link when it has leads, plain div when empty
Mirrors [[Mobile lead card is itself the click target — no View/Delete buttons]] for the OTHER mobile card type at the top of the Client Admin's card stack (one per Facebook Lead Ads source, above the per-lead cards). When `$source->leads_count > 0` the card is a real `<a href="{{ route('tenant-leads.source', $source) }}" wire:navigate>` with no View All button — tapping anywhere opens that source's spreadsheet. When `leads_count === 0` it stays a plain `<div>` (nothing exists yet to view) and keeps its own Delete button (`confirmDeleteSource`), gated by `canDeleteLeads` same as before — that button was never in scope to remove, only the View All one. The desktop table (a separate, unshared markup block further down in the same file) still renders both View All and Delete per row unchanged — tests that count occurrences of either string across the whole rendered response must account for the desktop copy still being there (see FacebookLeadAdsSpreadsheetTest's mobile-card tests, which count exactly 1 "View All" / 2 "confirmDeleteSource" wire:click occurrences, not 0/1).

## Leads table skeleton: wire:loading pairs scoped to $listLoadingTargets
The Client Admin leads table (both the `sm:hidden` mobile card stack and the desktop `flux:table`) has a skeleton loading state, shown only while `$this->leads` is actually being refetched — not on unrelated requests this same component handles (opening the New Lead modal, export, per-row delete, alert-switch toggles), which a bare untargeted `wire:loading` would also trip.

Wiring: a single `$listLoadingTargets` string (defined once in the page's top `@php` block, alongside `$hasActiveFilters`) lists every action that re-queries the list — the 7 filter properties from `FiltersLeadsQuery`/`updating()`'s reset-page array (`status,priority,sourceType,assignedTo,fromDate,toDate,search`) plus every pagination-trait method the published pagination view can call (`gotoPage,previousPage,nextPage,setPage`) plus `setPerPage` (called from this page's `x-init`, not a `wire:click`, but still a real Livewire method call `wire:target` can match). Every real-content element gets `wire:loading.remove wire:target="{{ $listLoadingTargets }}"`; every skeleton element gets `wire:loading` with the same target.

If you add a new filter or a new way to change the list (a sort control, a saved-view switcher, ...), add its property/method name to `$listLoadingTargets` too — otherwise that action either won't show the skeleton, or (worse) an unrelated action will.

Mobile: the real `@forelse` is wrapped in a single `<div wire:loading.remove ... class="contents">` (display:contents so it doesn't disturb the stack's own flex/gap layout) rather than repeating the attributes per-card, since Alpine/Livewire can't put directives directly on a `@forelse` block.

Desktop: can't use the same wrapper-div trick inside `<tbody>` (a `<div>` there gets foster-parented out by the browser, breaking the grouping) — instead: `wire:loading.remove`/`wire:target` go directly on the real `<flux:table.row>` tags (both the lead row and both `@empty` rows), and the skeleton is a *second* `<flux:table.rows>` (a second `<tbody>` — valid HTML, a table can have several) placed after the real one, carrying `wire:loading` at the tbody level instead of per-row.

## flux:table is table-fixed with no widths — pin them with a colgroup when rows toggle visibility
Flux's `<flux:table>` renders `table-layout: fixed` with no explicit column widths (see vendor's `table/index.blade.php`). Under fixed layout, browsers derive each column's width from whichever row happens to be the first *visible* one in the render tree — normally stable, since all rows share the same shape. But this page toggles row visibility via `wire:loading`/`wire:loading.remove` (see the skeleton rule in `.ai/rules/resources-views-livewire-tenant.md`), so the "first visible row" changes depending on loading state: the always-visible Facebook Lead Ads aggregate row vs. a real lead row vs. a skeleton row, each with very different content widths. Left unpinned, the header, the live rows, and the skeleton bars all disagreed on column x-positions during loading — confirmed from a user screenshot.

Fixed with an explicit `<colgroup>` (7 `<col class="w-[X%]">`, summing to 100%) as the first child of `<flux:table>`, before `<flux:table.columns>` — HTML requires colgroup immediately after any caption and before thead/tbody. This pins every column's width unconditionally, independent of which rows exist in the render tree at any moment. If a column is added/removed, update the colgroup's `<col>` count and percentages to match — a mismatched count re-opens the exact same instability.

Separately: the Facebook Lead Ads row/card (both desktop `<flux:table.row>` and the mobile `<a>`/`<div>` card) is NOT covered by any of `$listLoadingTargets` — it's a separate, unpaginated computed property search/filters don't touch — so it deliberately stays real content during loading rather than being replaced by a skeleton. But left at full opacity, live content sitting directly above skeleton placeholders read as broken. It now carries `wire:loading.class="opacity-40 pointer-events-none" wire:target="{{ $listLoadingTargets }}"` so it dims in step with the skeleton instead.

## Colgroup alone isn't enough for table-fixed column widths — Firefox needs it on the header th too
Follow-up to the earlier colgroup rule in this file: a `<colgroup>` with percentage `<col class="w-[X%]">` widths fixed the header/live-row/skeleton column misalignment in Chromium, but NOT in Firefox — confirmed via a user's Firefox DevTools screenshot showing the colgroup correctly present in the DOM (right position, correct classes) while columns remained visibly unaligned. Firefox (Gecko) doesn't reliably apply percentage `<col>` widths under `table-layout: fixed` in this setup.

Fix: pin the SAME widths on every `<flux:table.column>` header cell too (`class="w-[10%]"` etc., matching the colgroup's `<col>` values) — the header row is the "first row" `table-layout: fixed` always uses to lock column tracks, and unlike colgroup-only sizing, per-cell width on the actual first row is reliably honored across both engines. Both mechanisms are kept (redundant, not contradictory) rather than dropping the colgroup — if column count or proportions change, update both the `<colgroup>`'s `<col>` list and the header cells' width classes together, or they'll drift out of sync and reintroduce the exact bug this fixes.

## Never use bare wire:loading/wire:loading.remove on table-structural or display:contents elements
SUPERSEDES the two earlier rules in this file about colgroup/header-width fixing skeleton column misalignment — those were treating a symptom. The actual root cause, traced through Livewire's JS source (`toggleBooleanStateDirective` in `vendor/livewire/livewire/dist/livewire.esm.js`): a bare `wire:loading`/`wire:loading.remove` (no `.class` modifier) sets `el.style.display` directly, and its supported display list is only `inline, list-item, block, table, flex, grid, inline-flex` — anything else (including the `table-row-group`/`table-row` a `<tbody>`/`<tr>` needs, or `contents`) falls back to forcing `display: inline-block`. That breaks a `<tbody>`/`<tr>` out of the table's row-group layout entirely, so its cells stop honoring the table's fixed column widths — this, not any `<col>`/browser quirk, was what caused the header, live rows, and skeleton bars to visibly disagree on column positions (confirmed by reproducing the exact bug against the live app with a delayed-XHR Playwright harness, and by tracing Livewire's source directly).

Worse: the fallback isn't cleanly scoped to "while loading" either — due to how the function recomputes/caches the display value across a request's start and end, a plain `wire:loading.remove` element gets permanently pinned to `display: inline-block` after the **first completed loading cycle**, not just during subsequent ones.

Fix used throughout this file: never target `.remove`/bare `wire:loading` at a `<tbody>`, `<tr>`, or a `display:contents` div. Always use `wire:loading.class="!hidden"` (hide-during-loading) or `wire:loading.remove.class="!hidden"` (hide-by-default, `!hidden` baked into the static `class` list, removed while loading) instead — `.class` only ever touches `classList`, never `el.style.display`, so it can't hit this fallback. The `!` (important) prefix is required so the toggle reliably wins regardless of what other display-affecting classes (`flex`, `contents`, `table-row`, ...) are also present, without depending on Tailwind's internal class source-order.

The `<colgroup>`/header `w-[X%]` width-pinning added earlier is harmless and still present (redundant defense, doesn't hurt), but was NOT the actual fix — don't bother adding more of it if a future column-alignment bug appears; check for a bare `wire:loading`/`.remove` on a table-structural element first.

## Flyout close must use wire:model.live, not deferred wire:model
The lead detail flyout's <flux:modal variant="flyout" wire:model.self="showLeadPanel"> looked correct and had full, passing server-side test coverage (Index::updated() already nulls openLeadId — the #[Url(as: 'lead')]-bound query param — whenever showLeadPanel goes false) — but the bug still reproduced live in a browser: closing via the X button, Escape, or a backdrop click all close the flyout purely client-side (Alpine), and a PLAIN wire:model.self (no .live) is deferred — it updates the entangled value locally but does not send it to the server until some LATER, unrelated request happens to piggyback it along. Until then updated() never runs, so the ?lead= query param is left stale: the flyout looks closed but a refresh right afterward reopens it.

Confirmed via a Playwright network trace: clicking the close button fired zero Livewire requests before the fix. Changed to wire:model.live.self="showLeadPanel" — opening already round-trips server-side via viewLead() itself (which sets showLeadPanel true and re-renders), so .live only adds one extra request specifically on close, which is exactly what's needed. Verified all three close paths (X button, Escape, backdrop click) each now fire a request and correctly clear the URL.

General lesson: a Livewire test suite exercising the server-side property (->set('prop', false)->assertSet(...)) proves the PHP logic is correct, but does NOT prove the actual browser-side trigger (a third-party component's internal close mechanism) ever reaches the server at all — that needs a real browser/network check, not just a green Livewire::test() run.
