# Show Paneltenant Leads Partials

## Skeleton loading coverage across the Lead Management module — status and the one deliberately-skipped spot
Extends the skeleton-loading recipe (`.ai/rules/livewire-livewire.md`) to the rest of the Lead Management module, at the user's request to cover every card/table backed by dynamic DB data across Platform Admin, Client Admin, and Client User surfaces. All use the same `$initialLoadComplete`/`wire:init="completeInitialLoad"`/`$showSkeletonByDefault` mechanics as the three earlier views (main table/Kanban/FB spreadsheet).

**Done, lightweight variant** (no filters exist on these pages, so `$listLoadingTargets` is just `'completeInitialLoad'` — no property list to build): `Tenant\LeadSources\Index` (read-only table), `Platform\Clients\LeadSources` (per-tenant lead source config table — the pipeline-status picker and currency checkboxes above it are NOT gated, they're the small global catalog, not this tenant's own list), `Platform\LeadManagement\Settings` (both the statuses and currencies catalog tables).

**Done, Show.php's Activity feed**: `Show::activity()` (status logs + assignments + notes + detail-update logs merged — a genuinely unbounded, always-growing-over-a-lead's-lifetime feed, unlike the small catalogs above) is gated the same way. Non-obvious wrinkle: the Activity tab's badge count (`show.blade.php`) reads `count($this->activity)` UNCONDITIONALLY on every render (not just when that tab is open), so it had to be changed to render blank instead of a misleading "(0)" while `! $initialLoadComplete`. `activity-card.blade.php` (shared by both `show.blade.php`'s tab and `show-panel.blade.php`'s always-visible flyout column) computes its own `$listLoadingTargets`/`$showSkeletonByDefault` locally rather than requiring callers to pass them — both callers need the identical pair, so self-computing avoids duplicating it in two places.

**Deliberately NOT done: `Show::timeline()`** (the message/attachment conversation feed, rendered in `detail-card.blade.php`). Don't attempt this with a quick copy-paste of the pattern — `detail-card.blade.php`'s outer branch is `@if (count($lead->messageTimeline()) > 0)`, which checks the raw model method directly, NOT `$this->timeline` (the computed property that merges in attachments). Gating `timeline()` alone would leave that branch still evaluating true (genuinely has messages) while the inner `@foreach ($timeline as $item)` iterates an empty deferred array — rendering a blank box instead of a skeleton, a visible regression instead of an improvement. Fixing this properly needs the outer condition and the skeleton to agree on the same loading state, plus separate skeleton shapes for the card's other mutually-exclusive branches (Facebook Instant Form fields, email body view, plain message+attachments) — real design work, not a drop-in of the established recipe.
