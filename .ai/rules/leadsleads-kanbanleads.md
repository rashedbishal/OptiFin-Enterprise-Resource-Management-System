# Leadsleads Kanbanleads

## Skeleton also shows on first page load via wire:init + $initialLoadComplete gate
Beyond showing the skeleton on search/filter/pagination (see the other skeleton rules in this file), the Leads table, the Client User Kanban board, and the Facebook Lead Ads spreadsheet ALL also show it on the very first page load/refresh, not just later interactions — a genuine deferred-load architecture, not a CSS trick.

Mechanism (`Index`/`SourceLeads` both): a `public bool $initialLoadComplete = false` property, flipped true by a trivial `completeInitialLoad()` method, triggered via `wire:init="completeInitialLoad"` on the view's root element (Livewire dispatches this as a real request right after the component mounts client-side). The query method(s) that actually fetch leads (`Index::filteredQuery()`, shared by `leads()`/`boardLeads()`/`boardLeadCounts()`; `SourceLeads::leads()` directly) short-circuit to a guaranteed-empty `->whereRaw('1 = 0')` query until that flag is true — keeps the first HTTP response cheap regardless of tenant size. `completeInitialLoad` is added to each page's `$listLoadingTargets` so the exact same skeleton/dimming toggles already used for filters also cover this state, no separate mechanism.

`SourceLeads::fieldColumns()` is deliberately NOT gated behind this flag (unlike `leads()`) — it needs to return the true Instant Form field set immediately so the header's column count is stable before and after loading, rather than growing once real data arrives.

Kanban-specific: `Index::filteredQuery()` being gated means `boardLeads()` is empty during the initial phase, which would trip `leads-kanban.blade.php`'s top-level `@if ($this->boardLeads->isEmpty())` empty-state branch on every fresh load — fixed to `@if ($initialLoadComplete && $this->boardLeads->isEmpty())`. Desktop board columns already render unconditionally per `tenantLeadStatuses` (real, ungated, cheap metadata) regardless of lead count, so only each column's inner content (count badge + card list) needed a real/skeleton toggle. Mobile's status groups are skipped when empty (`$columnLeads->isNotEmpty()`) as a deliberate, untouched steady-state behavior — so the mobile skeleton is a separate, parallel block that unconditionally shows all `tenantLeadStatuses` while loading, since which statuses will actually have leads isn't knowable yet.

Test fallout: `Livewire::test(Index::class)`/`test(SourceLeads::class, [...])` now needs `->call('completeInitialLoad')` chained on (or `boardLeads`/`leads`/`boardLeadCounts` will assert against the guaranteed-empty pre-load state) — already added across the existing suite. Any NEW test touching these computed properties needs it too. Exception: a test that asserts an immediate `abort()`/404 from `mount()` (a non-existent lead source, wrong type, etc.) must NOT chain `->call('completeInitialLoad')` — the component never reaches a valid post-mount state to call it on.

## wire:loading toggles need a server-known default too, or the empty state flashes before hydration
Follow-up bug to the `$initialLoadComplete`/`wire:init` rule in this file: `wire:loading.class`/`wire:loading.remove.class` only take effect once Livewire's JS actually dispatches a request. There's a real gap between the browser painting the raw SSR'd HTML and the `wire:init="completeInitialLoad"` request firing — during that gap, NEITHER toggle has run yet, so both sides render their untoggled default: the skeleton block (baked-in `!hidden`, revealed only on loading) stays hidden, and the real-content block (visible by default, hidden only on loading) stays visible — showing its genuinely-empty pre-`initialLoadComplete` state, i.e. "No leads yet" flashing before the skeleton ever appears. Caught via user report ("why it is showing no leads yet first"), confirmed by sampling the DOM every ~20ms in the first 300ms after paint with the wire:init round-trip artificially delayed.

Fix: a `$showSkeletonByDefault = ! $initialLoadComplete` computed once per page (alongside `$listLoadingTargets`), used to make the STATIC baked-in class on both sides conditional on server-known state at render time — no JS timing dependency possible. Real-content wrappers get `{{ $showSkeletonByDefault ? '!hidden' : '' }}` (or `@class(['!hidden' => $showSkeletonByDefault])` on Flux components); skeleton wrappers get the inverse. The existing `wire:loading.class`/`.remove.class` toggles are left untouched — once `initialLoadComplete` is permanently true, `$showSkeletonByDefault` is permanently false and everything reverts to the original defaults, with wire:loading alone correctly handling every subsequent search/filter/pagination transition.

Applies to every real/skeleton pair introduced for this: leads.blade.php's mobile "contents" wrapper, desktop per-row `!hidden`, desktop `@empty` rows, desktop skeleton `<tbody>`; leads-kanban.blade.php's desktop per-column and mobile status-group real/skeleton pairs; source-leads.blade.php's equivalents. If a new real/skeleton pair is added to any of these pages, it needs this same `$showSkeletonByDefault`-conditional static class — not just the `wire:loading` toggle — or it will reintroduce this exact flash.

Trap hit while writing this: writing the literal substring `@php` inside a `{{-- Blade comment --}}` breaks compilation (`Unmatched ')'`) — Blade's `@php`/`@endphp` directive matching isn't comment-aware, it applies even inside `{{-- --}}`. Avoid the literal token `@php` in comment prose; say "PHP block" instead.
