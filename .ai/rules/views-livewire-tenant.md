# Views Livewire Tenant

## Client Admin leads table's per-page size is viewport-driven, not fixed
Index::$perPage (default 15) feeds leads()'s ->paginate($this->perPage) instead of a hardcoded number. The server can't see the viewport, so it can't pick 15 (desktop table) vs 10 (mobile card stack) on first render — the view's root div has x-init that calls $wire.setPerPage(10 or 15) based on a `(max-width: 639px)` matchMedia query (the same `sm` breakpoint the view already switches the table/card-stack layout at), plus a `change` listener on that same MediaQueryList so resizing across the breakpoint updates it live. Index::setPerPage() ignores any value other than 10/15 (never trust it as arbitrary client input) and resetPage()s + unsets the leads computed property so the size change takes effect from page 1. This means the very first paint (before Alpine runs) always uses 15, even on mobile — one extra Livewire round trip happens immediately after load to correct it. That's an accepted trade-off, not a bug to fix.

## Client Admin leads table: free-text search box, full-width row at every breakpoint
Index::$search feeds filteredQuery() (Index-specific, like $sourceType — not the shared FiltersLeadsQuery trait, since SourceLeads/the Kanban board don't need this exact box) with a grouped OR across identifier/name/phone/email/company/location, plus win_probability/deal_value cast via `CAST(... AS TEXT)` since those are numeric DB columns and Postgres (unlike MySQL/SQLite) refuses to LIKE-compare a numeric column directly. The whole OR chain is wrapped in its own `where(function...)` closure — an ungrouped orWhere() chain here would escape the surrounding tenant/source-type AND conditions, same precedence bug class already fixed once in SendLeadAlertNotifications. 'search' was added to both the `updating()` and `updated()` reset-page arrays alongside status/priority/sourceType/assignedTo/fromDate/toDate. In leads.blade.php, the `<flux:input wire:model.live.debounce.400ms="search">` carries `col-span-2 md:col-span-3 lg:col-span-1` — its own full-width row below the dropdowns/dates on mobile and tablet, but a normal single cell at `lg` and up, where the grid grows to `lg:grid-cols-7` (one more than the 6 dropdown/date fields) specifically so the box sits in the *same* row as everything else on desktop, per explicit request — don't put it back on its own row at that breakpoint. This box only exists on the Client Admin's table (leads.blade.php) — leads-kanban.blade.php (Client User's board) has its own separate, shorter filter grid with no search box, even though the same $search property and filteredQuery() logic would apply to it too if ever set; there's just no UI control for it there by design, matching what was actually asked for.
